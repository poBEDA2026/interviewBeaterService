# InterviewBeaterService — дизайн-документ

> Дата: 2026-08-25
> Статус: все 5 секций утверждены автором (2026-08-25)
> Цель: приложение для подготовки к Java-собеседованиям (позиция middle/middle+). Двойная цель: рабочий инструмент ежедневной подготовки + витрина компетенций для рассказа на собеседованиях.

## Зафиксированные решения

| Вопрос | Решение |
|---|---|
| Функциональность | Инкрементально: каталог вопросов → SRS (интервальное повторение) → статистика → AI-интервьюер последним этапом. Каждый инкремент — самостоятельный рабочий продукт |
| Форма | REST API + веб-UI |
| Архитектура (масштаб) | Модульный монолит → позже вынести AI-модуль в микросервис с брокером сообщений (выбор: Kafka) |
| Пользователи | Мультипользовательский, Spring Security + JWT, изоляция данных |
| Данные | Минимальный фикстурный набор (~50 вопросов: Core Java, Spring, SQL), наполнение по ходу работы |
| Внутренняя архитектура | Классическая слоистая (web → service → repository), package-by-feature |

## Технологический базовый уровень

- Java 21 LTS — производственный стандарт до 2028, безопасный выбор для собесов ([bluepes](https://bluepes.com/blog/why-java-21-is-still-the-enterprise-standard))
- Spring Boot 4.1.x — актуальная версия (4.1.0, июнь 2026) ([spring.io](https://spring.io/projects/spring-boot))

## Секция 1: Общая архитектура и модули ✅

**Название проекта:** `interviewBeaterService` (отображаемое имя; artifactId в Maven — `interview-beater-service`, kebab-case по конвенции).

Модульный монолит, **package-by-feature** — модули по бизнес-возможностям, внутри каждого классические слои:

```
interviewBeaterService/
├── shared/                  ← общее: исключения, DTO-мапперы, утилиты
├── security/                ← JWT, Spring Security config, User
├── question/                ← каталог вопросов
│   ├── web/                 ← QuestionController, DTO
│   ├── service/             ← QuestionService (бизнес-логика)
│   ├── repository/          ← Spring Data JPA
│   └── domain/              ← Question, Tag, Difficulty (enum)
├── review/                  ← SRS-движок
│   ├── web/                 ← ReviewController (сессия повторения)
│   ├── service/             ← ReviewService, Sm2Service
│   ├── repository/
│   └── domain/              ← ReviewSchedule, ReviewGrade
├── statistics/              ← прогресс и аналитика
│   ├── web/
│   ├── service/             ← слушает доменные события
│   └── repository/          ← проекции/агрегаты
└── ai/                      ← этап 4: AI-интервьюер (потом → микросервис)
```

### Ключевые архитектурные решения (темы для собеседования)

1. **Package-by-feature, не by-layer** — все слои фичи рядом. Легко вырезать модуль при выносе в микросервис → прямое обоснование будущей миграции AI-модуля.
2. **Связь модулей через сервисные интерфейсы + Spring Events** — `review` публикует `QuestionReviewedEvent`, `statistics` его слушает. Модули не знают внутренностей друг друга; при выносе AI-сервиса событие переедет в Kafka — код `statistics` почти не изменится.
3. **SRS-алгоритм (SM-2) — отдельный Spring-бин без состояния** — чистая функция над доменной моделью: легко юнит-тестировать, легко заменить на другой алгоритм (FSRS) — паттерн Strategy.

### Поток данных (пример)

`POST /api/reviews/{id}/grade` → `ReviewController` → `ReviewService` (валидация, транзакция) → SM-2 пересчитывает интервал → `ReviewScheduleRepository` сохраняет → публикация `QuestionReviewedEvent` → `StatisticsService` обновляет агрегаты — асинхронно, в той же транзакции (позже — `@TransactionalEventListener(AFTER_COMMIT)` + Kafka).

## Секция 2: Стек и инструменты ✅

| Слой | Технология | Зачем на собесе |
|---|---|---|
| **Ядро** | Java 21, Spring Boot 4.1, Maven | База. Java 21 = virtual threads, records, pattern matching |
| **Web** | Spring MVC + virtual threads (`spring.threads.virtual.enabled=true`) | Топ-тема: «зачем WebFlux, если есть виртуальные потоки» |
| **Доступ к данным** | Spring Data JPA + Hibernate, JPA Specifications + Pageable | Динамическая фильтрация; N+1, `@EntityGraph`, кэши L1/L2 |
| **БД** | PostgreSQL 17 (Docker), Flyway, HikariCP | Миграции, пулы соединений, tuning |
| **Кэш** | Redis + `@Cacheable` (агрегаты статистики) | Кэширование, TTL, invalidation |
| **Security** | Spring Security 7 + JWT через oauth2-resource-server (валидация) + jjwt (выдача) | Современный способ без кастомных фильтров; refresh-токены |
| **API-контракт** | springdoc-openapi (Swagger UI), Bean Validation, Problem Details (RFC 9457) | Стандартные ошибки API |
| **UI** | Thymeleaf + htmx + Pico.css | Серверный рендеринг; фокус на Java |
| **Маппинг** | MapStruct | Compile-time маппинг vs reflection |
| **Тесты** | JUnit 5, Mockito, AssertJ, Testcontainers, срезы `@WebMvcTest`/`@DataJpaTest`, JaCoCo | Testcontainers vs H2 — топ-вопрос |
| **Качество** | Spotless + Checkstyle, GitHub Actions CI | Пайплайн, статический анализ |
| **Наблюдаемость** (этап 3+) | Actuator + Micrometer + Prometheus + Grafana | Метрики, health checks |
| **Отказоустойчивость** (этап AI) | Resilience4j: retry, circuit breaker, rate limit на клиенте LLM | Защита от нестабильного внешнего сервиса |
| **Асинхронность** (этап AI) | Kafka + `@TransactionalEventListener` | Эволюция Spring Events → Kafka |

**Осознанно не берём:** WebFlux (домен блокирующий), QueryDSL (не развивается), микросервисы с первого дня, event sourcing. Lombok берём (уметь сказать, чем он плох).

**Принцип:** каждый инструмент привязан к инкременту, ничего «на будущее» (YAGNI).

## Секция 3: Модель данных ✅ (тезисы — конкретные решения принимает автор)

Что нужно спроектировать и о чём подумать:

- **Определить сущности** под функциональность этапов 1–3: пользователи, вопросы с категоризацией, состояние повторения, история повторений, агрегаты статистики. Сущности AI-этапа проектируются при его реализации (YAGNI). Имена в схеме секции 1 — иллюстративные, рабочие названия выбирает автор.
- **Определить связи** между сущностями и их кратность (User–Question–повторение — центральная связка).
- **Продумать разделение**: mutable-состояние алгоритма повторения vs immutable-журнал фактов (источник истины для статистики).
- **Продумать индексы** под главные запросы: «какие вопросы пора повторить», уникальность пары пользователь×вопрос.
- **Продумать общий банк вопросов vs личные вопросы** пользователей.
- **Продумать типы**: enum'ы в БД (строки vs ordinal), хранение markdown-ответов.
- **Продумать конкурентность**: параллельная оценка одного вопроса (оптимистичная/пессимистичная блокировка).
- **Продумать, как хранить агрегаты статистики** (денормализованные проекции, пересобираемые из журнала).
- Все решения зафиксировать в Flyway-миграциях.

## Секция 4: API и SRS-движок ✅ (тезисы)

### REST API — какие возможности должны быть закрыты

- **Auth:** регистрация; логин с выдачей JWT; refresh-токен (продумать отзыв/ротацию).
- **Каталог (этап 1):** CRUD вопросов; фильтрация по категории/сложности/тегам + поиск по тексту; пагинация и сортировка. Продумать, кто может редактировать общие вопросы (роли).
- **Повторение (этап 2):** «что повторить сегодня» (очередь due-вопросов); отправка оценки ответа; инициализация расписания при первом знакомстве с вопросом; отложить/заморозить вопрос.
- **Статистика (этап 3):** суммарный прогресс; прогресс по категориям; динамика по дням; «слабые места».
- **Общие требования:** префикс `/api/v1`; Swagger UI; Bean Validation на входах; ошибки в формате RFC 9457; изоляция данных пользователя.

### SRS-движок

- Алгоритм SM-2 как stateless-бин за интерфейсом (Strategy) — замена на FSRS без правки вызывающего кода.
- Продумать самостоятельно: шкалу оценок (маппинг на 0–5 SM-2); граничные интервалы; критерий «выучен»; поведение при провале (сброс интервала, lapses).
- После каждой оценки — доменное событие (секция 1).

### Веб-UI

- Логин/регистрация; список вопросов с фильтрами; карточка вопроса; экран сессии повторения (главный): вопрос → «показать ответ» → самооценка → следующий; дашборд прогресса.
- htmx для интерактива без SPA.

## Секция 5: Безопасность, ошибки, тестирование, инкременты ✅ (тезисы)

### Безопасность

- Пароли — BCrypt; токены: короткоживущий access + refresh.
- Продумать самостоятельно: хранение и ротация refresh-токенов, отзыв (logout), ограничение попыток логина, 404 vs 403 при доступе к чужим данным.
- Роли USER/ADMIN; админ-операции над общим банком вопросов.
- Секреты — вне кода (env/`.env` в docker-compose), в git не попадают.

### Обработка ошибок

- Централизованный обработчик (`@RestControllerAdvice`) + иерархия своих исключений.
- Единый формат ошибок RFC 9457 (Problem Details): type, title, status, detail.
- Продумать маппинг: валидация → 400 с перечнем полей, not found → 404, конфликт конкурентности → 409, внутренняя ошибка → 500 без стека наружу.

### Тестирование — пирамида

- **Unit (большинство):** SRS-алгоритм — параметризованные тесты на граничные значения; сервисы с Mockito.
- **Срезы:** `@WebMvcTest` (валидация, статусы, RFC 9457), `@DataJpaTest` (индексы, уникальность).
- **Интеграционные (меньше):** `@SpringBootTest` + Testcontainers (PostgreSQL, позже Redis) — сквозные сценарии.
- JaCoCo с порогом покрытия; CI на GitHub Actions: build + тесты на каждый пуш/PR.

### Инкременты — каждый этап самостоятельный рабочий продукт

| Этап | Что входит | Что рассказывать на собесе |
|---|---|---|
| **0. Каркас** | Spring Boot 4.1 + Java 21, docker-compose (Postgres), Flyway, CI, Checkstyle | Инфраструктура, CI |
| **1. Auth + каталог** | Security + JWT, CRUD вопросов, фильтры/пагинация, Swagger, RFC 9457, UI списка и карточки, seed ~50 вопросов | Security, JPA, миграции |
| **2. SRS** | SM-2, сессия повторения (главный экран), доменные события, optimistic locking | Алгоритм, конкурентность, events |
| **3. Статистика** | Проекции по событиям, Redis-кэш, дашборд, Actuator + Prometheus + Grafana | Кэширование, наблюдаемость |
| **4. AI-интервьюер** | LLM API-клиент, Resilience4j (retry/circuit breaker/rate limit), стриминг ответа | Интеграция с внешним API, отказоустойчивость |
| **5. Микросервис** | Вынос AI-модуля, Kafka между сервисами, `@TransactionalEventListener(AFTER_COMMIT)` | Эволюция монолита, асинхронщина, Kafka |

Правило: инструмент появляется в том этапе, где нужен — ничего «на будущее».

## Дополнительно к базовой настройке Spring (этап 0, по мере необходимости)

Настраивается не «на будущее», а когда появляется потребность (YAGNI):

| Возможность | Что даёт | Когда включать |
|---|---|---|
| **Профили** (`application-dev.yml`, `application-local.yml`) | Разные настройки для окружений: dev — `show-sql` и подробные логи, prod — чистый вывод | Как только настроек, отличающих окружения, становится больше одной |
| **Actuator** (`spring-boot-starter-actuator`) | Готовые эндпоинты `/actuator/health`, `/actuator/info`, метрики Micrometer | Этап 3 по плану (наблюдаемость), но `/health` полезен и раньше — для docker healthcheck и CI |
| **springdoc-openapi** | Swagger UI и OpenAPI-схема по контроллерам | Этап 1 — появляется вместе с первым REST-контроллером |

Все три — стандартные стартеры без собственной конфигурации на старте; детали (безопасность actuator-эндпоинтов, аннотации `@Operation` для Swagger) — в этапах, где они нужны.

## Следующие шаги

- Реализация идёт поэтапно, план реализации составляется отдельно на каждый инкремент (первый — этап 0 + этап 1).
- Пункты «продумать самостоятельно» — осознанная делегация автору: это часть подготовки к собеседованию.
